A Python API framework that checks its own architecture.

Typed Python declarations become one contract shared by routing, validation, access policies, transactions, OpenAPI and development tools. Optional rules check the architectural promises you make.

01 The problem

Architecture drifts. Hinoki turns each promise into a check.

  • ✕✓

    An endpoint that forgot its access policy is public by default.

    Declare access=; HNK-ACC-001 fails the check when it is missing.

  • ✕✓

    A write that should be atomic is not.

    Declare transaction=True; HNK-TXN-001 reports every state-changing action without it.

  • ✕✓

    A response leaks a token or a whole model.

    HNK-SCH-001 and HNK-API-001 keep named fields out of responses and models out of handlers.

  • ✕✓

    Layers drift: models start importing the API.

    HNK-IMP-001 reads the source files and reports forbidden imports.

Describe the table

A model is a typed class. Hinoki compiles its queries to SQL for PostgreSQL in the Rust ORM, and nothing touches a database at import.

State what crosses the boundary

Validation is strict, with no coercion. A response exposes only the fields its Schema names.

Declare the behaviour next to the action

Access, transactions and errors are options of the decorator, or defaults of a group. The same declaration feeds routing, the OpenAPI document and the rules.

05 Fit

Who it is for, and who it is not for yet.

A fit today

  • You are evaluating a typed Python API stack on PostgreSQL.
  • You want architectural promises that a tool can check, not only review.
  • You can use a source checkout and test against disposable data.

Not yet

  • Production use: the API and migration format may change.
  • Databases other than PostgreSQL.
  • Workloads that need end-to-end performance claims.
  • Implicit many-to-many relations and advanced relation paths.
