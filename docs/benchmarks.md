## One API. Two server setups.

Four framework stacks served the same small API and PostgreSQL data. These measurements describe one machine and one benchmark session; they do not rank frameworks or predict production performance.

## What was measured

One service, two tables and deterministic seed data: 100 authors and 10,000 posts, 80% published. Every stack had to match a PostgreSQL oracle and the same SQL statement count per request before measurement.

| Scenario | Request | What the service does |
| --- | --- | --- |
| `list` | `GET /posts?page=1&page_size=20` | Published posts with their author, newest first, in a page envelope with the total: one COUNT and one joined SELECT. |
| `detail` | `GET /posts/{id}` | One published post with its author: one joined SELECT. |
| `health` | `GET /health` | Static JSON, no database: a diagnostic of the framework and server path. |
| `create` | `POST /posts` | Validate the body, insert, return the post with its author: one INSERT and one author SELECT. |

| Stack | ORM and driver | Server | Versions |
| --- | --- | --- | --- |
| Hinoki | Hinoki ORM (Rust, tokio-postgres) | Granian (ASGI) | hinoki 0.0.1, granian 2.8.8 |
| FastAPI | SQLAlchemy async, asyncpg | Uvicorn with uvloop | fastapi 0.162.7, sqlalchemy 2.1.8, asyncpg 0.32.0, uvicorn 0.54.0 |
| Django Ninja | Django async ORM, psycopg 3 pool | Uvicorn with uvloop | django-ninja 1.8.0, django 6.1.3, psycopg 3.3.9 |
| Django Bolt | Django async ORM, psycopg 3 pool | its own Actix server | django-bolt 0.13.0 |

## How to read the numbers

- **Requests per second and latency are one measurement.** Every run keeps 64 connections busy, so higher latency means fewer requests per second; the two do not confirm each other.
- **Each chart starts at 0 and shows the median requests per second.** Bars are sorted from highest to lowest within a workload and server setup. Each panel has its own scale; use the tables for exact values and the lowest-to-highest run range.
- **p50 and p99 are medians of per-run percentiles**, not percentiles of all requests pooled together. A range is descriptive, not a confidence interval.
- **CV is the coefficient of variation of requests per second across runs.** Above 15% for any stack, the scenario is not reported: the samples are too unstable to compare, and the raw files are kept.
- **What this does not cover:** TLS, proxies, authentication, compression, memory, cold data, larger tables or other hardware. Pool sizes are equal per process, but each library schedules work differently.
