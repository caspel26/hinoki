# Project status

Hinoki is pre-alpha. The public API and migration format may change; this repository is not published on PyPI yet (its package name will be `hinoki-api`). The [`hinoki` project name](https://pypi.org/project/hinoki/) currently belongs to an unrelated legacy package. Use this repository's source checkout for evaluation and test against disposable data.

The [documentation site](documentation-versions.md) separates current development docs from release-tagged versions. Until the first release, the site root points to the `dev` docs.

## Implemented and exercised

The repository includes typed function and class endpoints, routes registered per app in `routes.py`, project-wide `middleware` and `rules` lists in `hinoki.toml`, optional model-backed CRUD route generation, request binding and strict schemas, built-in and custom Schema validation, bounded typed multipart uploads, opt-in Model write constraints and validators, access policies and declared errors, optional architecture rules, settings and worker modules, SQLite, PostgreSQL, MySQL and MariaDB ORM backends with relations, querysets and file-based migrations, sync and async handlers, atomic writes (`atomic=True` on actions, `db.atomic` as a block or decorator, sync and async), model lifecycle hooks with instance state and after-commit callbacks, typed events with explicit handlers (`in_transaction` and `after_commit`, declared per app in `hinoki.toml`; `Created`, `Updated` and `Deleted` model events from the model write path, and a model with handlers for one leaves the native lane for the matching generated action), `AuthRejected` and `RateLimited` events for refused requests (`after_commit` only, no credentials or paths in the payload; the `hinoki events` command lists the registered handlers), `bulk_create`/`bulk_update`/`bulk_delete` and their `abulk_*` forms (one transaction each), a runtime check of every response against its return annotation (startup errors for annotations that cannot be checked), route-level rate limit policies supplied by the application, OpenAPI, parsers, renderers, development and application MCP, and an optional admin with four styles, its own users, sign-in page, per-model permissions and shared sign-in limits, and `hinoki admin` commands.

The examples are the best way to see the pieces together, in three levels: [Notes](https://github.com/caspel26/hinoki/tree/main/examples/notes) (easy) is one app with generated CRUD; [Tracker](https://github.com/caspel26/hinoki/tree/main/examples/tracker) (medium) has several apps with explicit dependencies, access policies, transactions, a filtered list, events, and project-wide middleware and rules; [Blog](https://github.com/caspel26/hinoki/tree/main/examples/blog) (complete) adds a tenant, login, the admin, application MCP, a streamed export, an audit trail from events, a rule waiver and optional metrics. Each is a self-contained project with its own `hinoki.toml`, tests and README.

## Current boundaries

* SQLite, PostgreSQL, MySQL and MariaDB are supported ORM databases; SQLite is the local-development default. MySQL and MariaDB have separate real-server integration coverage in CI. SQL Server and Oracle are not supported. See the [database guide](databases.md) for backend-specific TLS, migration and feature limits, including MariaDB JSON behavior.
* Hinoki does not open database connections at import or apply migrations automatically.
* Rate limits: `RateLimit` counts in a shared database table (or in memory for development), counted in the Rust core on both the async and sync paths ([rate limit an action](endpoints.md#rate-limit-an-action)); a route can still name any other policy. The admin's sign-in uses a per-worker window by default and `DatabaseLoginWindow` for a limit shared by every worker ([limit sign-in attempts](admin.md#limit-sign-in-attempts)). There is no tracing integration or health route; Kiso's Prometheus metrics are in [export Prometheus metrics](metrics.md).
* The ASGI adapter and application handler calls run in Python, except for the Kiso native paths described below. The Rust extension provides path matching, selected query/header/cookie parsing, schema validation/serialization, cryptography and SQL ORM compilation/execution, and drives eligible generated CRUD writes and eligible `async def` ORM handlers.
* Built-in security settings add browser response headers, HSTS on effective HTTPS requests, and an opt-in `308` HTTPS redirect that requires explicit allowed hosts.
* Generated typing for some keyword-based ORM calls is less precise than model construction; see [typing](typing.md).
* Many-to-many relations are declared with `many_to_many(...)` on one model (a generated or adopted bridge table, bounded link sets, `within=` scopes, generated CRUD `<field>_ids`); an association model with extra columns is still written by hand. Through-model columns on the generated bridge, nested writes of related rows and many-to-many filters on admin lists are not available, and generated CRUD reads related rows only as ids. Routes with an ids field run natively when the targets are scoped with `all_rows(...)` or `own_rows(...)`, and a custom scope callable, a hook or a `Linked`/`Unlinked` handler keeps them on the Python lane.
* End-to-end performance claims are not made without comparable retained measurements; see the [benchmark report](benchmarks.md) and its limits.
* The default server is Kiso, Hinoki's Rust HTTP server (Granian stays available with `--server granian`, and any other ASGI server can run the app). It serves `serve` and `dev`: HTTP/1.1, optional TLS and, with `server.http2` over TLS, HTTP/2 (no h2c or server push; WebSocket upgrades only for `@http.websocket` actions, over HTTP/1.1), an access log (pretty, plain or JSON, with path exclusions and a slow floor), a startup banner naming Kiso, most request-pipeline work still runs in Python and so do handlers, except that an `async def` handler provably limited to ORM reads and stock writes (`atomic=True`, guarded and body routes included) is driven from Rust without an asyncio task ([native handler lane](kiso.md#the-native-handler-lane)), and eligible public generated `create`, `update` and `delete` actions run their transaction in Rust ([generated CRUD](kiso.md#generated-crud)); no performance figure is claimed. Kiso applies host, CORS preflight and HTTPS-redirect policies natively before its optional `startup_url` probe; the probe reports startup completion, not general application or database health. See [Kiso](kiso.md).
* The server adapter is ASGI. `hinoki.wsgi.WSGIAdapter` wraps an application for WSGI servers (buffered bodies; an application with a streamed action is refused at start); verified with Granian only, see [serving](serving.md#wsgi).
* Actions can stream: `Stream`, `EventStream` (server-sent events) and `File` are sent while they are produced, on Kiso and on Granian, with a bounded buffer, an idle timeout, keep-alive comments and a disconnect check; the stream count, the file lookup, the length check and the SSE frames are Rust on both servers; see [stream a response](streaming.md) for what runs in Rust and what stays in Python. Streamed actions are not available through `WSGIAdapter`, `atomic=True`, MCP or the native lane. WebSockets (`@http.websocket`, see [WebSockets](websockets.md)) run on Kiso, with framing and limits in Rust, and on Granian through the ASGI `websocket` scope, where only the Origin check and the message size are enforced by Hinoki; they are not available through `WSGIAdapter` or over HTTP/2.
* Kiso can export Prometheus metrics from a dedicated listener (`metrics.listen`, off by default; Kiso only, and `hinoki serve --server granian` refuses it). The registry, the exposition and the cross-worker merge are Rust; only the settings are Python. Event handler runs are recorded into the same registry (`hinoki_events_total`, `hinoki_event_handler_duration_seconds`). See [export Prometheus metrics](metrics.md). No overhead figure is claimed for requests; the cost per event handler run is measured in [that page](metrics.md#event-handlers).
* Outbound email is SMTP only (`smtp`, plus `console` and `memory` for development and tests), sent from a per-worker `Mailer` on the same worker loop; the message render, the SMTP conversation, TLS, the pool and retries are Rust. There is no queue, no guaranteed delivery (`possibly_sent` marks the ambiguous case), no SMTPUTF8, XOAUTH2, DKIM or inline images, no HTTP providers, and the admin sends no email in 0.1.0. Email templates are a small fixed language (values, `if`, `for`) rendered in Rust with typed contexts checked at worker startup, and `hinoki mail check` and `hinoki mail preview` run them from the CLI. See [send email](email.md) and [email templates](email-templates.md).
* Kiso can compress response bodies with brotli or gzip (`compression.enabled`, off by default; Kiso only, and `hinoki serve --server granian` refuses it): negotiation of `accept-encoding`, `Vary`, size and content-type rules, `no-transform`, streams, event streams and files, a flush whenever a stream pauses, and a bound on concurrent compressions are Rust; only the settings are Python. See [compress responses](compression.md). No compression ratio or throughput claim is made beyond the measurement stated there.
* CORS is an application-wide policy in the `cors` settings group, and an action, a `RouteGroup` or `crud(...)` can replace it with `cors=http.Cors(...)` ([per-route CORS](web-security.md#cors-per-route)). Application MCP has its own allowed-origin check. Pagination uses page numbers by default, and cursor (keyset) pagination is available for generated and handwritten lists.
* Generated `crud(...)` lists accept client filters, ordering and search declared in a `FilterSet` (`filters=`): `Eq`, `In`, `Range`, `.null`, `Search` and an `ordering` allow-list, parsed and compiled to predicates in Rust, applied on top of `get_queryset`, with typed OpenAPI parameters and cursors bound to the filters. Operators beyond those, filters across relations and filters on the admin lists are not provided. See [CRUD](crud.md#filter-order-and-search-the-list).
* Pagination page-size defaults are `20` and `100`; the `pagination` settings group changes them for the whole app and an action's own `PageNumberPagination` values win. See [pagination](pagination.md).
* OpenAPI generation writes an OpenAPI 3.2 document (3.1 with `docs.openapi_version`), creates operation IDs and reads summary/description from handler docstrings; an action can set `tags`, `deprecated`, `operation_id` and `include_in_schema` ([per-action controls](openapi.md#per-action-controls)). `QUERY` actions are the `query` operation in 3.2 and `x-query` in 3.1 ([the document version](openapi.md#the-document-version)). Top-level tag descriptions are not available.
* There is no maintained Docker image or deployment recipe. `hinoki serve` runs the app on Kiso by default, or on Granian with `--server granian`; container packaging and process orchestration are application deployment choices.

See the [roadmap](https://github.com/caspel26/hinoki/blob/main/ROADMAP.md) for project direction and [contributing](https://github.com/caspel26/hinoki/blob/main/CONTRIBUTING.md) for local checks.
