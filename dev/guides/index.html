Guides

Guides¶

Updated November 24, 2026 5 min read

One page per task. Start with data and endpoints, then add access, rules and runtime concerns as you need them. New to Hinoki? Take the tutorial or the quick start first, or read the examples in order: Notes (easy), Tracker (medium) and Blog (complete), plus the focused Mailroom (outbound email).

Data¶

  • Configure a databasechoose the backend, set the URL or connection fields, keep credentials secret.
  • Define modelscolumns, primary keys, column types, table names and write-time validators.
  • Model optionsindexes, composite uniqueness, default order, update timestamps and names, as decorators.
  • Relationsforeign keys, one-to-one, many-to-many association models and explicit loading.
  • Query and write rowsfilters, pagination, reusable queries, creates, updates and bulk writes.
  • Lifecycle hooksreact to a model's own writes and inspect its changed columns.
  • Eventstyped events with explicit handlers that run inside the transaction or after the commit.
  • Migrationsplan, review, apply and check migrations for every app.
  • Schemasdeclare the data that crosses the API boundary and convert it to and from rows.
  • Scalar field typesenums, literals, dates, decimals, bytes, addresses, secrets and paths.
  • Collections and unionssets, tuples, dictionaries, unions, discriminated unions, TypedDicts and dataclasses.
  • Validate inputconstraints, normalization, field and object checks, and input reshaping.
  • Schemas from modelsderive a Schema from a Model and convert rows with from_model.
  • Time and utilitiesUTC time, the application timezone, test clocks and update timestamps.

Endpoints¶

  • Function-based APIsthe default pattern: plain functions grouped by a RouteGroup that states access, transactions and errors once.
  • Class-based APIsAPI classes for @crud resources with hooks, inheritance and resources you ship to others.
  • Register routeshow routes.py and hinoki.toml build the route map, with Mount, include= in tests and hinoki routes.
  • Requests and responseswhat an action receives (path, query, body, forms, XML, files) and how its result is checked.
  • Store uploaded filesbounded memory or local-disk storage with opaque keys and streamed downloads.
  • Generate CRUD routeslist, retrieve and write actions from a model, with access and ownership rules.
  • Errorsmalformed requests, authentication failures and declared application errors.
  • Stream a responseStream, EventStream and File answers sent while they are produced, on Kiso and Granian.
  • WebSockets@http.websocket actions with Access, typed JSON messages, limits and back-pressure, on Kiso and Granian.
  • Compress responsesoptional brotli and gzip compression of bodies, on Kiso only.
  • Export Prometheus metricsrequest counters and histograms on a dedicated listener, on Kiso only.
  • Middlewaretyped Middleware around an action or the whole app, identical on Kiso and Granian.
  • Paginationpage-number pagination with PageNumberPagination and keyset cursors with CursorPagination.
  • Filter, order and search a CRUD listFilterSet with Eq, In, Range, Search and an ordering allow-list.
  • Parsers and renderersother body formats in and out.
  • OpenAPI documentthe OpenAPI 3.2 document (3.1 on request) generated from routes, signatures and Schema declarations.

Security and checks¶

  • Authentication and accessproviders resolve a Caller; Access policies check permissions.
  • Application sessionsserver-side state, cookie lifecycle, CSRF checks, session authentication and explicit stores.
  • Hosts, CORS and HTTPSrestrict the host names an app answers to, which browser origins may read it, browser security headers, HTTPS redirects and trusted proxies.
  • Rulestyped promises about your application, checked with a stable ID, a location and an explanation.

Runtime¶

  • Application modulesresources that live as long as a worker, such as a database pool.
  • Cache valuesbounded Rust memory cache or a shared database backend with explicit TTL and failure behavior.
  • Transactionsatomic=True on actions, db.atomic in application code.
  • Settingstyped, immutable settings from the environment, dotenv and TOML, with redacted secrets.
  • Serve an applicationhinoki dev while you work, hinoki serve in production, on Kiso (the default) or Granian.
  • Kiso serverwhat Hinoki's Rust server runs natively, its limits, workers and signals, reload and reverse-proxy behaviour.
  • Test an applicationtest through the whole stack with ASGIClient, against a disposable database, from the test hinoki new generates.
  • Command lineevery hinoki command, the short forms inside a project and the explicit forms outside one.
  • Create a projectthe interactive hinoki new flow, its options and what the generated project contains.
  • Inspect an applicationcheck rules, list routes, export the OpenAPI document, show settings and diagnose the environment.
  • Interactive shellan async-capable prompt with the app's settings and models.
  • Typingwhat a type checker catches in handlers, decorators and Schema construction.

Integrations¶

  • Add an adminstaff pages for your models, with a sign-in page, users and per-model permissions.
  • Customize the admincolumns, hooks, bulk actions, templates and themes.
  • Send emailSMTP, console and memory backends from a per-worker mailer, sent after a commit; no queue.
  • Email templatestyped TOML templates rendered in Rust, checked at startup and previewed from the CLI.
  • Expose actions over MCPselected actions as tools for a remote MCP client.
  • Development MCPa server that describes your app to a coding agent; it can run requests against the app only when you enable --scenarios.
  • Build with a coding agenta project, rules and tools ready for an agent, the llms.txt files and Markdown mirrors of these docs, and where its authority ends.

Operating¶

  • Best practicesproject structure, Schema contracts, Access policies, queries, Rust fast paths, testing and production operations.
  • Sync and async codethe event loop, the bounded sync pool and which style each surface accepts.
  • Benchmarksretained measurements with their environment, method and limits.
  • Changelogevery user-facing change, explorable by version and type.
  • Native CRUD orientation runa workload-specific measurement of generated CRUD.
