3.1 · Guides

Guides¶

One page per task. Start with data and endpoints, then add access, rules and runtime concerns as you need them. New to Hinoki? Take the tutorial or the quick start first.

Data¶

  • Configure a database: choose the backend, set the URL or connection fields, keep credentials secret.
  • Define models: columns, primary keys, column types, table names and write-time validators.
  • Model options: indexes, composite uniqueness, default order, update timestamps and names, as decorators.
  • Relations: foreign keys, one-to-one, many-to-many association models and explicit loading.
  • Query and write rows: filters, pagination, reusable queries, creates, updates and bulk writes.
  • Lifecycle hooks: react to a model's own writes and inspect its changed columns.
  • Migrations: plan, review, apply and check migrations for every app.
  • Schemas: declare the data that crosses the API boundary and convert it to and from rows.
  • Scalar field types: enums, literals, dates, decimals, bytes, addresses, secrets and paths.
  • Collections and unions: sets, tuples, dictionaries, unions, discriminated unions, TypedDicts and dataclasses.
  • Validate input: constraints, normalization, field and object checks, and input reshaping.
  • Schemas from models: derive a Schema from a Model and convert rows with from_model.
  • Time and utilities: UTC time, the application timezone, test clocks and update timestamps.

Endpoints¶

  • Function-based APIs: the default pattern: plain functions grouped by a RouteGroup that states access, transactions and errors once.
  • Class-based APIs: API classes for @crud resources with hooks, inheritance and resources you ship to others.
  • Register routes: how routes.py and hinoki.toml build the route map, with Mount, include= in tests and hinoki routes.
  • Requests and responses: what an action receives (path, query, body, forms, XML, files) and how its result is checked.
  • Generate CRUD routes: list, retrieve and write actions from a model, with access and ownership rules.
  • Errors: malformed requests, authentication failures and declared application errors.
  • Pagination: page-number pagination with PageNumberPagination.
  • Parsers and renderers: other body formats in and out.
  • OpenAPI document: the OpenAPI 3.1 document generated from routes, signatures and Schema declarations.

Security and checks¶

  • Authentication and access: providers resolve a Caller; Access policies check permissions.
  • Hosts, CORS and HTTPS: restrict the host names an app answers to, which browser origins may read it, browser security headers, HTTPS redirects and trusted proxies.
  • Rules: typed promises about your application, checked with a stable ID, a location and an explanation.

Runtime¶

  • Application modules: resources that live as long as a worker, such as a database pool.
  • Transactions: atomic=True on actions, db.atomic in application code.
  • Settings: typed, immutable settings from the environment, dotenv and TOML, with redacted secrets.
  • Serve an application: hinoki dev while you work, hinoki serve in production, on Kiso (the default) or Granian.
  • Kiso server: what Hinoki's Rust server runs natively, its limits, workers and signals, reload and reverse-proxy behaviour.
  • Test an application: test through the whole stack with ASGIClient, against a disposable database, from the test hinoki new generates.
  • Command line: every hinoki command, the short forms inside a project and the explicit forms outside one.
  • Create a project: the interactive hinoki new flow, its options and what the generated project contains.
  • Inspect an application: check rules, list routes, export the OpenAPI document, show settings and diagnose the environment.
  • Interactive shell: an async-capable prompt with the app's settings and models.
  • Typing: what a type checker catches in handlers, decorators and Schema construction.

Integrations¶

  • Add an admin: staff pages for your models, with a sign-in page, users and per-model permissions.
  • Customize the admin: columns, hooks, bulk actions, templates and themes.
  • Expose actions over MCP: selected actions as tools for a remote MCP client.
  • Development MCP: a read-only server that describes your app to a coding agent.
  • Build with a coding agent: a project, rules and tools ready for an agent, and where its authority ends.

Operating¶

  • Sync and async code: the event loop, the bounded sync pool and which style each surface accepts.
  • Benchmarks: retained measurements with their environment, method and limits.
  • Generated CRUD on the native path: a workload-specific measurement of generated CRUD.
  • Troubleshooting: common errors by their message.
  • Toolchain and CI: local and CI commands for contributors.

Concepts and project¶

  • Concepts: how models, Schema classes, actions, workers and rules fit together.
  • Request lifecycle: the order of routing, access, binding, handler, commit and response.
  • Structure an application: layers, where each concern lives, and why.
  • Glossary: one word, one meaning.
  • Use other libraries: what owning Schema and Model means, and the extension points.
  • Reference: public names, signatures and docstrings.
  • Status: what works today and what does not yet.
  • Documentation versions: how dev and release docs are published.
