3.12 · Guides

Validate input¶

A Schema validates in three stages: Rust checks types and Field(...) constraints, then @field_normalize canonicalizes values, then @field_check and @object_check reject what the rules forbid. All failures are returned together in errors.ValidationError.details, and a request answers 422.

Built-in and custom validation¶

# notes/apps/accounts/schemas.py
from typing import Annotated

from hinoki import Field, Invalid, Schema, field_check, field_normalize, object_check

Username = Annotated[str, Field(min_length=3, max_length=32, pattern=r"[a-z0-9_]+")]


class Registration(Schema):
    username: Username
    email: Annotated[str, Field(format="email", max_length=254)]
    password: Annotated[str, Field(min_length=12, max_length=128)]
    confirmation: Annotated[str, Field(max_length=128)]

    @field_normalize("email")
    def lowercase_email(self, value: str) -> str:
        return value.lower()

    @field_check("password")
    def reject_common_password(self, value: str) -> None:
        if value.lower() in {"password12345", "qwerty123456"}:
            raise Invalid("common_password", "choose a less common password")

    @object_check
    def passwords_match(self) -> None:
        if self.password != self.confirmation:
            raise Invalid(
                "password_mismatch", "passwords do not match", path="confirmation"
            )
Tool Runs Use for
Field(...) first, in Rust lengths, pattern, numeric bounds, one_of, format (email, url, slug, hex_color)
Field(strip=, lower=, upper=) before every other check trimming and case folding of str
@field_normalize("f") after structural validation typed canonical form; the result is checked against the same constraints
@field_check("f") after normalization rejecting one value
@object_check after field checks rules across fields
  • Checks raise Invalid(code, message, path=...) and return None; a non-None return or an async method is a programming error.
  • Normalizers are typed synchronous methods returning str; they cannot reject input or rescue a value that failed structural validation.
  • All three run for Schema.validate(...), Schema(...) and from_model(). They never run on a Model: model writes have their own constraints and validators.
  • No I/O and no side effects. Rules that depend on current data belong in an operation.

Normalize text¶

class Signup(Schema):
    handle: Annotated[str, Field(strip=True, lower=True, min_length=3, max_length=32)]


Signup.validate({"handle": "  AbC "}).handle  # "abc"

strip removes what str.strip() removes; lower and upper follow str.lower()/str.upper(). Constraints see the normalized text, and a custom normalizer receives it. Only str fields accept these options; lower and upper together, or a one_of value the normalization would change, raise RegistrationError. Results are the same on both lanes and for direct construction. The OpenAPI document describes the constraints, not the normalization.

Reshape input with @before_validate¶

from typing import Any

from hinoki import before_validate


class Profile(Schema):
    display_name: Annotated[str, Field(max_length=80)]

    @before_validate
    @classmethod
    def accept_legacy_name(cls, data: dict[str, Any]) -> dict[str, Any]:
        if "name" in data and "display_name" not in data:
            rest = {key: value for key, value in data.items() if key != "name"}
            return {**rest, "display_name": data["name"]}
        return data


assert Profile.validate({"name": "Ada"}).display_name == "Ada"
  • Runs on the decoded mapping before structural validation, on this schema and every nested one, on both lanes; base-class hooks first.
  • The data is untrusted: check types first. It is a shallow copy; replace nested values instead of mutating them. Synchronous, no I/O.
  • Invalid(...) answers 422; KeyError, TypeError, ValueError, IndexError or AttributeError answer invalid_input, not 500.
  • A plain union of schemas with such a hook is refused: use a discriminated union. On a plain method the decorator raises RegistrationError.

Which lane runs what¶

Types and Field(...) constraints are checked in Rust on the Python-object path and, for most schemas, on the GIL-free JSON path. The decorators are Python callables: they run only on values that passed the Rust stage. Checks of nested Schema values run through lists and dicts at any depth.

Text that cannot be stored¶

A string or dict key containing NUL (\u0000) is refused with nul or key_nul on both lanes, after the length checks and before pattern: PostgreSQL cannot store NUL in text. A string that is not valid Unicode (a lone surrogate) is refused with type.
