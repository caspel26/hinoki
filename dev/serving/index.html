3.21 · Guides

Running an application¶

cd examples
uv run --project .. hinoki dev   blog.main:create_app     # development: reload on change
uv run --project .. hinoki serve blog.main:create_app     # production-style: no reload

TARGET is module:name, where name is an application (Hinoki) or a function that returns one (a factory: the usual choice, because it builds the app inside each worker). The factory builds declarations only; databases and pools open in the worker's lifespan.

With a declared app, settings load when the target module creates the Hinoki object. The database declared by the settings (or a configured DatabaseModule) opens that worker's pool during lifespan startup and closes it during shutdown. The pool is per worker; no database connection is opened by importing model or route modules. See settings and database ownership.

Both commands run the app on the Kiso unless you choose Granian with --server granian or server.server. In the Hinoki checkout, uv sync --locked installs the development environment, including Granian and its reload support. A project created by hinoki new declares the server extra in its source dependency; run uv sync in that project. hinoki new --server granian (or the server prompt) writes a settings.toml that makes the project run on Granian instead of Kiso. The extra includes Granian's reload support (watchfiles), which hinoki dev needs. If Granian was installed separately without watchfiles, dev reports the missing dependency and serve still works. For this checkout, use its locked source environment instead of installing hinoki[server] from the public package index; see installation for setup.

Where host, port and workers come from¶

From the application's server settings group (settings guide); flags override them:

Setting Variable (prefix BLOG_) Default Flag
server.host BLOG_SERVER__HOST 127.0.0.1 --host
server.port BLOG_SERVER__PORT 8000 --port
server.workers BLOG_SERVER__WORKERS 1 --workers (serve)
server.runtime_threads BLOG_SERVER__RUNTIME_THREADS 1
server.backlog BLOG_SERVER__BACKLOG 1024
server.access_log BLOG_SERVER__ACCESS_LOG unset Unset logs in hinoki dev only (or whenever access_log_format is set); true or false decides for both
server.access_log_skip BLOG_SERVER__ACCESS_LOG_SKIP unset Kiso only: comma-separated paths the log leaves out (health checks); exact, or a prefix when the entry ends with *
server.server_timing BLOG_SERVER__SERVER_TIMING unset Kiso only: add a Server-Timing header (kiso;dur=3.2;desc="native": milliseconds the server took and the serving lane); unset means hinoki dev only
server.recent_requests BLOG_SERVER__RECENT_REQUESTS unset Kiso only: file that also receives each request as a JSON line, read by the recent_requests tool of hinoki mcp; rotated near 1 MiB
server.access_log_slow_ms BLOG_SERVER__ACCESS_LOG_SLOW_MS unset Kiso only: keep only answers at least this slow, in milliseconds
server.access_log_format BLOG_SERVER__ACCESS_LOG_FORMAT unset Kiso only: pretty, plain, json or logger. Unset is pretty on a colour terminal and plain otherwise
server.server BLOG_SERVER__SERVER kiso --server

dev always runs one worker with reload. The settings command shows what is in effect: hinoki settings blog.settings:BlogSettings.

Before serving a deployment, narrow allowed_hosts to the names it answers to (BLOG_ALLOWED_HOSTS=app.example.com). While it is the default * and debug is off, each worker logs allowed_hosts is '*' and debug is off: ... at startup, on Granian, Kiso, WSGI and other ASGI servers alike.

Kiso¶

Kiso is Hinoki's own HTTP server, written in Rust on hyper, tokio and rustls. hinoki serve and hinoki dev run the application on Kiso, which is part of Hinoki's native extension, unless you choose Granian with --server granian or server.server = "granian". Choose Granian when you need an ASGI wrapper around the app (see below), or a server outside the extension.

uv run --project .. hinoki serve blog.main:create_app --server kiso
uv run --project .. hinoki serve blog.main:create_app --server kiso --workers 4
uv run --project .. hinoki dev   blog.main:create_app --server kiso

from hinoki import settings


class BlogSettings(settings.AppSettings, prefix="BLOG_"):
    server: settings.ServerSettings = settings.ServerSettings(server="kiso", workers=4)

What is native and what still runs in Python¶

The listener, HTTP/1.1 parsing, connection and header limits, body framing and its limits and timeouts, route matching, the request ID, and the answers that need no application code run on the native runtime without taking the Python interpreter lock. Without host, CORS or HTTPS-redirect policies, a request the native layer can answer by itself is answered there: unknown paths and methods (404, 405 with Allow), oversized request lines or headers, 503 while the worker is not ready or the in-flight limit is reached, and malformed requests. When one of those policies is active, the Rust classifier still checks it first, then preserves Python lookup for unmatched requests. The response carries the same security headers, request ID, CORS and HSTS policy as one produced by the application.

The lifespan, documentation and OpenAPI pages, handwritten handlers and their database calls still use Python. Host allow-list checks, CORS preflight answers and HTTPS redirects run in the Rust classifier before docs and route lookup, with the same response order and headers as the Python pipeline. For matched routes that continue through the Python pipeline, Kiso also percent-decodes the captured path values and passes them to Python; an invalid UTF-8 escape is carried as an error marker and reported at the same point where the pipeline previously decoded it. Python still applies str, int, UUID, bool and custom converters, and owns authentication, hooks, body/query binding, handlers, error translation and response assembly.

For an eligible public GET, DELETE, POST, PUT, PATCH or QUERY function, Kiso skips Python route matching and request binding. It accepts parameters from the path and query string annotated str, int, float, bool or UUID with the built-in converter, and query parameters whose default has exactly that type. Rust decodes provided values, converts them with the same rules as the Python converters (an invalid value gives the same 422), validates the full query, negotiates Accept, and prepares the handler arguments. An absent optional query uses its declared default, including when a wrapper observes the keyword arguments; an empty value is still an explicitly supplied empty string. Missing required or repeated query parameters use the same validation response as the Python pipeline. Error translation and Response creation remain in Python; JSON encoding uses Hinoki's Rust encoder, and Rust finalizes the response headers and suppresses the body for HEAD. Those final headers include the CORS headers for the request's Origin, on successful and error answers alike, exactly as the Python pipeline adds them; an answer that sets its own Access-Control-Allow-Origin keeps its CORS headers. An async handler runs in its ordinary asyncio task, unless it qualifies for the native handler lane; a sync handler uses the bounded executor. If a sync handler returns an awaitable, Hinoki awaits it on the same request task after the executor call completes. An integer longer than 18 digits is left to the Python pipeline, which applies Python's own integer limits. A body method is eligible with exactly one Schema body parameter and only built-in parsers (JSONParser, FormParser, TextParser, BytesParser, exact types without overrides; a custom parser or a JSONParser.prepare override uses the Python pipeline). The route's parser is chosen from the Content-Type after the body is read, so an unlisted type is the same 415. Its body is read from the native connection only when the handler's turn comes, after content negotiation, with the same limits, and is then decoded and validated by the Rust decoder and validator. The failures keep the order and the answers of the Python pipeline: a declared length above the limit or a body read failure first, then a malformed query string, then the content type (415) and malformed JSON (400), then one 422 listing every path, query and body problem in declaration order. A refusal before the body is read closes the connection, as on the Python pipeline. The automatic path does not accept several body parameters, file or Request parameters, custom parsers, multipart uploads, defaults on path parameters, custom response headers or custom renderers. The built-in JSONRenderer, HTMLRenderer, TextRenderer and XMLRenderer, alone or several on one route, are eligible: Rust negotiates Accept (including 406) and Python renders with the chosen one, exactly as on the Python pipeline. A subclass of a built-in renderer or one with extra attributes is custom. A route with an access policy stays eligible, with at most one Caller principal parameter: Python authenticates the request before anything else, so the order of the answers (400, invalid_query, 401/403) matches the Python pipeline, and the body is still read only after authentication succeeds. A route with a rate_limit policy is eligible too: Python asks the policy, with the same client address as the Python pipeline (the forwarded client when the TCP peer is a trusted proxy, otherwise the peer) and the authenticated caller, right after authentication and before negotiation, the body and validation, so a refused client gets the same 429 or 503 without the server reading its body. A route with atomic=True stays eligible: the handler runs inside the same transaction as on the Python pipeline, the commit follows the encoding of the answer, and any error or timeout rolls back before it is translated. Host restrictions, CORS and HTTPS redirects are checked natively and do not make an otherwise eligible route fall back. Every other route uses the full Python request pipeline for binding, validation, error translation and response assembly. The request body is read natively only when that pipeline asks for it, after authentication, so an unauthenticated client cannot make the server buffer a body. Handlers themselves remain Python code; this is not an application written in Rust, and no performance figure is claimed here. A Query[Schema] parameter of a GET or DELETE is eligible too (Python converts and validates the query string, reporting errors in the pipeline order; it does not combine with a body). A Form[Schema] or XML[Schema] body is eligible too: the text is converted and validated as described in Form bodies and XML bodies.

The native handler lane¶

An async def handler that only reads the database through the ORM can run without an asyncio task: Kiso drives its coroutine itself, runs each database wait on the native runtime and sends the answer from there. Hinoki decides this once per route at worker startup, by reading the handler's own source: the route must be an unguarded GET or DELETE (no access, rate_limit, Query[Schema] or several renderers, no atomic), the function must be a plain async def (not wrapped by a decorator), and every await in it must be an ORM read on a Model class: Model.aget(...), Model.aget_or_none(...), or Model.filter(...) / Model.all() with filter, order_by, limit and offset, ending in aget, afirst, acount or aexists, or awaited directly. Writes (acreate, aupdate and the like), async with, async for, yield, async comprehensions, local names that shadow a model, and any other await (asyncio.sleep, an HTTP client, another coroutine) keep the route in an asyncio task. hinoki routes --lanes shows the choice, and hinoki.runtime logs the reason for every route at debug level.

The behaviour is the same on both paths: status, headers, body, error translation, the request ID and the request_timeout (a 504). Each request has its own context, so request_id and the database are the ones of that request. The handler's steps after its first run on the event-loop thread, so a task it starts still finds the loop. If a driven handler awaits something only asyncio can run (a database backend without native waits), it is moved to an asyncio task at that point and continues with what is left of the request timeout. At shutdown, running handlers are cancelled like request tasks.

What it assumes: model classes and their ORM methods are not replaced after startup. Set server.native_dispatch = false to keep every handler in an asyncio task. No performance figure is claimed here.

Generated CRUD¶

Generated CRUD plans can also execute public create (POST), update (PATCH) and delete actions in Rust. These routes use the native path only when their model and schemas are supported and they have no assignment rule or custom CRUD hook (an owner is allowed only with identity_key = caller_id, a text non-key column outside the update schema, on any supported database), and their access policy, if any, uses an unmodified ClaimsJWTAuth. Rust reads and validates the bounded request body, runs the database transaction, fetches the written row where the response requires it, and encodes the response before commit. Writes continue to completion if the client disconnects. A unique-constraint violation returns 409 Conflict by default; a registered application error handler takes precedence. Routes that are ineligible or become stale use the ordinary Python CRUD pipeline. Plans are selected automatically at worker startup and checked once per second; a changed plan is disarmed until the worker restarts. This path adds no public setting.

The measured phase 1 path is documented in the native CRUD orientation run. It is a single-host, workload-specific measurement and does not establish general or production performance.

Optional startup probe¶

Hinoki(startup_url="/health") reserves one public, fixed GET/HEAD endpoint and returns {"status":"ok"} after that worker's lifespan startup has completed. The setting is off by default. Its path must be a literal ASCII path; query strings, fragments, parameters, percent escapes and dot segments are rejected. It must not match an application route or an enabled OpenAPI/docs path. The endpoint is not an application route and does not appear in OpenAPI or generated CRUD/MCP tools.

This is a startup probe, not a general readiness or liveness check. A 200 says that startup completed (and, on Kiso, its request wake reader was installed); it does not check database availability, downstream services, request capacity, or whether the Python event loop continues to make progress. It answers independently of the Python request queue when Kiso can apply the response directly. Before readiness it returns 503 not_ready; during shutdown readiness is cleared before graceful draining begins.

ASGI/Granian and WSGI answer it in the Python pipeline after host, CORS and HTTPS-redirect checks. Kiso checks host restrictions, answers CORS preflights and redirects plain HTTP requests on its Tokio thread before it considers the probe. GET and HEAD negotiate application/json and validate query syntax; other methods return 405 with Allow: GET, HEAD, unless CORS answers a preflight first. WSGI reads request bodies before the pipeline, so its body-size behavior differs from Kiso for a body sent to this GET/HEAD endpoint. WSGI also starts lazily on the first request and uses its adapter-level 503 if startup fails. Since WSGI exposes a decoded PATH_INFO rather than the raw request path, percent-encoded aliases may be indistinguishable from the literal probe path there.

Limits¶

  • HTTP/1.1, plus HTTP/2 over TLS when server.http2 is on (see below). No WebSocket or other protocol upgrades: an Upgrade header is ignored and the request is answered as plain HTTP, and the server never answers 101. There is no cleartext HTTP/2 (neither prior knowledge nor Upgrade: h2c).
  • A request line plus headers larger than execution.max_header_bytes, or a query longer than execution.max_query_bytes, is refused (431, 414). A body larger than execution.max_body_bytes is refused with 413, by Content-Length before any byte is read or, for chunked bodies, as soon as the total passes the limit. A client that sends nothing for body_read_timeout seconds (10 by default, never more than half of execution.request_timeout) gets 408.
  • A client that does not finish its request headers within header_read_timeout seconds (10 by default) is disconnected; the same timer closes idle keep-alive connections.
  • TLS is optional: set server.tls_cert_file and server.tls_key_file (PEM; the key may be PKCS#8, PKCS#1 or SEC1) and Kiso speaks HTTPS with rustls (TLS 1.2 and 1.3, the library's default cipher suites, no client certificates, ALPN http/1.1, or h2 then http/1.1 with server.http2). The files are read once at start, so a renewed certificate needs a restart (a rolling restart of the workers is enough). A plaintext client on a TLS port gets a TLS alert, never an answer, and the handshake must finish within header_read_timeout. Requests over TLS have the scheme https, so the HSTS policy applies. Granian takes the same two settings (the framework asks it for TLS 1.2 and up and HTTP/1.1 only, as Kiso does, unless server.http2 is on). A trusted proxy's X-Forwarded-Proto overrides the scheme, http included, on both servers. The handshake and the request head each have their own header_read_timeout, so a slow client can hold a connection slot for up to twice that time. Behind a proxy that terminates TLS, leave them unset and list the proxy in trusted_proxies instead.
  • HTTP/2 is opt-in: set server.http2 = true together with the TLS files (it is a settings error without them, on both servers). The server then offers ALPN h2 and http/1.1 and serves each connection with the protocol it negotiated; a client that offers only http/1.1, or no ALPN, still gets HTTP/1.1. Requests reach the application unchanged, with http_version 2 in the ASGI scope; the :authority pseudo-header becomes the Host and wins over a host header that differs. Limits are fixed, not settings: 32 concurrent streams per connection (the 33rd is refused), a 64 KiB stream window, header lists bounded by execution.max_header_bytes and at most 100 header lines per request (cookie fields count once; more is answered 431), and the h2 library's rapid-reset protections. A connection counts as one slot of max_connections, but every stream in flight uses backend capacity (the in-flight limit and the queue) like a request of its own, so size those limits for connections times 32. The server also drops a connection on which more than 100 streams end before their response completed (client resets) within a fixed 10-second window; it is closed without a GOAWAY. The count is per connection, not per client: a client can pass about twice the bound across a window boundary, and a new connection starts from zero. A connection with no open stream for header_read_timeout is closed gracefully (GOAWAY; a stream opened in the race with the GOAWAY is accepted and then cut when the shutdown timeout ends). A response that sends no data for write_timeout seconds (a client that keeps its flow-control window at zero, or stopped reading) also gets the connection a GOAWAY: hyper cannot reset one stream from outside, so the other streams have the shutdown timeout to finish and the stalled one is cut with the connection. Progress is tracked per response, so opening new streams does not hide a stalled one. Keep-alive pings every 30 seconds drop a peer that stopped answering. Set write_timeout above 32 x 16 KiB divided by the slowest client bandwidth you expect to serve: HTTP/2 shares the window between streams unevenly, so on a slow link each of 32 concurrent downloads can wait that long between two chunks and be taken for stalled while bytes still flow. A request with several host headers and no :authority is refused with 400. A client that trickles the head of one stream while others are open is not bounded by header_read_timeout. On stop the server sends GOAWAY, lets streams in flight finish, and aborts what is left after the shutdown timeout. Not provided: cleartext HTTP/2 (h2c), server push, and WebSocket or CONNECT over HTTP/2. Granian with server.http2 negotiates HTTP/2 itself (http mode auto), under its own limits.
  • A client that stops reading a response for write_timeout seconds (30 by default) is disconnected; any progress restarts the timer.
  • max_connections (10000 by default) bounds open connections. Requests waiting for the application are bounded by an in-flight limit and a queue; beyond them the answer is 503.
  • Requests with ambiguous framing (for example Content-Length together with Transfer-Encoding, repeated lengths, or a bare line feed in the head) are refused with 400 and the connection is closed.
  • On start, Kiso names itself on stderr before the listening on ... line (which stays on stdout, where tools wait for it): its version, the mode (serve or dev, which reloads on file changes), the worker count, the scheme, whether the access log is on and whether the native handler lane is on. In a terminal (and with NO_COLOR unset) it is two lines with the name in bold; otherwise it is one plain line, for example Kiso 0.1.0 (Hinoki's own server): serve, 4 workers, http, access log off, native lane on.
  • The access log is one line per answered request, written to stderr by Kiso: 127.0.0.1:52341 - "GET /items?limit=5 HTTP/1.1" 200 OK 3.2ms. The time is how long the server took to decide the answer, not including writing it to the client, and the line is printed for every answer, including the ones the server gives itself (404, 429, 503). When stderr is a terminal (and NO_COLOR is unset) the line is coloured in the style of a development console: INFO: in green, the request in bold, the status by class (2xx green, 3xx cyan, 4xx yellow, 5xx red) and the time dimmed. Control characters in the target are shown as \xNN. server.access_log_format = "json" writes one JSON object per line instead, for a log pipeline: {"time":"2026-11-19T19:56:25.881Z","peer":"127.0.0.1:52341","method":"GET","path":"/items","query":"limit=5","http_version":"1.1","status":200,"duration_ms":3.2,"lane":"python"}; time is RFC 3339 UTC, lane says where the request was first routed (early for an answer from the transport or the classifier, python, or native for the native handler lane) and route is the pattern that matched, e.g. /items/{id}, so requests can be grouped without parsing paths (absent when no route matched) and quotes and control characters are escaped. server.access_log_format = "logger" hands each request to the Python hinoki.access logger instead of writing to stderr, so your own handlers, formatters and filters (see your own loggers) decide where it goes; each record carries the JSON fields as record.access. Kiso queues up to 4096 records and a logging thread passes them to Python in batches, taking the GIL once per batch; when the logger falls behind, new records are dropped rather than slowing requests. Setting a format turns the log on, in serve too, unless access_log is false. access_log_skip = ["/health", "/static/*"] leaves noisy paths out and access_log_slow_ms = 100 keeps only slow answers; failures (status 400 and up) are always logged.
  • A client that disconnects does not cancel its running handler; the handler finishes and its answer is discarded.

Settings that apply to one server only¶

hinoki serve refuses a setting the chosen server cannot honour, by name, and exits with status 2; it never ignores it or falls back to the other server.

Setting Kiso Granian
host, port, workers, runtime_threads, backlog, access_log, trusted_proxies, request_id_header, trust_request_id applied applied
max_connections, header_read_timeout, body_read_timeout, write_timeout, native_dispatch, access_log_format, access_log_skip, access_log_slow_ms, recent_requests, server_timing applied when set refused when set

If the native extension of a build has no Kiso, --server kiso fails with an error that says so.

Workers, signals and restarts¶

With one worker hinoki serve runs the server in its own process. With several workers (and always under hinoki dev) it starts a supervisor that opens the listening socket once (honouring backlog), starts each worker as a fresh process that imports the target and builds the application, and passes the socket down. Workers share the one socket, so connections are spread by the operating system's accept; Hinoki does not balance them. Databases and pools open inside each worker's lifespan, never in the supervisor.

  • SIGTERM, SIGINT (Ctrl-C) or SIGHUP stops accepting, lets running requests finish for up to lifecycle.shutdown_timeout, runs the lifespan shutdown and exits. A worker still running five seconds after that is killed. A second signal kills the workers immediately. Once the stop begins the supervisor closes its own copy of the socket, so a client that connects while the workers drain is refused. --workers must be 1 to 256 (0 uses server.workers).
  • A worker that exits on its own, whether it failed to start or crashed, is not restarted: the supervisor stops the other workers and exits with a non-zero status. Restart policy belongs to the process manager (systemd, a container runtime) that runs hinoki serve.
  • The listening socket is opened before the lifespan startup of a supervised worker finishes, so connections wait in the backlog until a worker accepts them. With one worker the socket is opened after a successful startup.
  • If the supervisor is killed without a chance to clean up, its workers notice within a second of finishing their startup and stop. The workers' copy of the listening socket is not inherited by processes a handler starts.
  • A socket that cannot be opened (address in use, a bad port or host) is reported as error: cannot listen on HOST:PORT: ... with exit status 2, with one worker or several.

hinoki dev --server kiso¶

The supervisor watches the project directory (*.py, *.toml and .env files; .venv, .git and caches are ignored) and, on a change, stops the worker gracefully and starts a new one on the same socket, so a client connecting during the restart waits instead of being refused. If the new code fails to import or start, the error is printed (a short error: cannot load ... line for a missing module or name, a traceback for other failures), waiting for changes follows, and the next edit starts the worker again; connections wait in the meantime. The host, port, backlog and the choice of server are read once when hinoki dev starts: change them and restart the command. The other server settings (limits, trusted_proxies, runtime_threads) are read again by every restarted worker. The watcher ignores .venv but not a virtual environment with another name, such as venv/: keep it outside the project directory or it triggers reloads. The first import of the target happens in the command itself, so an error there stops it with a message instead of waiting. dev needs watchfiles (the hinoki[server] extra) and uses one worker.

Behind a reverse proxy¶

server.trusted_proxies works as described in settings: the native layer matches the TCP peer against it for the request ID and the HSTS and scheme policy of its own answers, and the request pipeline resolves the forwarded scheme and client address of the requests it handles from the same peer. The rate limit of a natively served route resolves its client the same way, so RateLimitContext.client is the same on both lanes. Two points to know:

  • Entries are IP addresses or CIDRs. An IPv6 address with a zone id such as fe80::1%lo0 is refused when settings load, for either server (earlier versions loaded it and the ASGI path matched it; Kiso cannot take it).
  • On a listener bound to :: that also accepts IPv4 (the default on many systems, for example Linux with bindv6only=0 and macOS), an IPv4 peer appears as ::ffff:a.b.c.d. A plain IPv4 entry such as 10.0.0.5 or 10.0.0.0/8 then never matches, and the proxy is treated as untrusted. That fails closed, and the ASGI path behaves the same. Either bind an IPv4 host (--host 0.0.0.0) or list the mapped form, for example ::ffff:10.0.0.0/104.
  • A request ID that a trusted proxy sent and Hinoki refused is logged as ignored invalid request ID from trusted proxy; for requests answered natively the warning is aggregated once a second with a count.

Declaring where settings are read¶

The settings class says its own prefix and .env file, so nothing is repeated at the call site:

from hinoki import settings


class BlogSettings(settings.AppSettings, prefix="BLOG_", dotenv=".env"):
    database_url: settings.Secret


app_settings = BlogSettings.load()  # reads BLOG_* and .env

Other runners¶

dev and serve are conveniences. The application is a plain ASGI app, so granian --interface asgi --factory blog.main:create_app (or another ASGI server) works too; run that command from examples/ with the locked environment active. The server group is ignored, because only hinoki serve applies it.

Metrics and tracing¶

Hinoki ships no metrics registry, exporter or tracing integration, and no health route besides the optional startup probe. On an ASGI server the application is a plain ASGI callable, so wrap it with the instrumentation you already use, or with a few lines of your own:

import time


class Timing:
    """Report each request's method, status and duration to ``record``."""

    def __init__(self, app, record):
        self.app, self.record = app, record

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http":
            await self.app(scope, receive, send)
            return
        started, status = time.monotonic(), None

        async def watch(message):
            nonlocal status
            if message["type"] == "http.response.start":
                status = message["status"]
            await send(message)

        try:
            await self.app(scope, receive, watch)
        finally:  # status stays None when the request was aborted before a response began
            self.record(scope["method"], status, time.monotonic() - started)


app = Timing(
    create_app(), record=my_metrics.observe
)  # run this with Granian or any ASGI server

What this measures is the time from the ASGI call to the last byte handed to the server, not what a client perceives. Keep method and status as labels; do not label by scope["path"] (it holds ids and has unbounded cardinality), the request ID (it is for correlating logs: logging.include_request_id adds it to each Hinoki log line) or the caller. Hinoki does not currently expose the matched route template to a wrapper, so per-route metrics need an application-level counter inside the handler or a gap report so a hook can be designed.

Kiso (--server kiso) has no ASGI boundary, so this wrapper does not apply to it and it has no instrumentation seam today. Use the server's own limits and the request log of your proxy, or serve with Granian when you need to wrap the application.

WSGI¶

ASGI is the intended way to serve Hinoki. When a deployment can only run WSGI, wrap the application:

# wsgi.py
from hinoki.wsgi import WSGIAdapter
from blog.main import create_app

wsgi_app = WSGIAdapter(create_app())

$ granian --interface wsgi wsgi:wsgi_app

The adapter drives the same ASGI callable on a background event loop that it owns, so routing, binding, access, errors, limits and the OpenAPI document behave as under ASGI. Specifics:

  • Startup is lazy. Modules (including the database pool) start on the first request of each worker process, so a pre-forking server can import the file in its master process. If startup fails, every request answers 503 with not_ready and the error is logged.
  • Shutdown runs on WSGIAdapter.close() or, otherwise, at interpreter exit. A server that kills workers without exiting normally skips it, as it would any atexit hook.
  • Async handlers run on the adapter's loop and sync handlers on the bounded executor, as under ASGI. Each WSGI server thread blocks for the duration of its request, so concurrency is the server's thread count rather than the event loop.
  • Bodies are buffered. Request bodies are read up to max_body_bytes plus one byte, so an oversized upload still answers 413. Responses are complete before they are sent; streaming responses are not available, and a client disconnect is not reported to the handler.
  • Paths. The server decodes the path once and the adapter passes it on without decoding again, so a client's %2520 reaches the handler as %20, as under ASGI. A percent-encoded slash (%2F) cannot be told apart from a real one in WSGI and is not available inside a path parameter. A bad Content-Length answers 400.
  • One protocol per process. Do not serve the same application object over ASGI and WSGI in one process; the adapter owns its own loop and module lifespan. Run two processes if you need both.

The path is checked against Granian's WSGI interface (--interface wsgi, with one and two workers), not against every WSGI server.
