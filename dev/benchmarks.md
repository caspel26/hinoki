# Benchmarks

<div class="bench-lead"><p class="bench-lead__what"><b>Measured:</b> requests per second and latency of 8 stack setups on 6 request types of one small API backed by PostgreSQL. <b>Where:</b> AMD EPYC-Milan Processor, 8 logical CPUs, Linux-7.0.0-30-generic-x86_64-with-glibc2.43, 2026-11-23 and 2026-11-24, 100 concurrent connections, median of 10 samples per cell.</p><p class="bench-lead__finding">Hinoki (Kiso, native server) against Hinoki (Granian): ahead in 5 of 6 request types, tied (within 10%) in 1, behind in 0.</p><p class="bench-lead__caveat">Pre-alpha software, one host, warm data, loopback network: this is not a ranking and not a production claim.</p></div>

<p class="bench-reading">Each cell is the median requests per second; higher is better. The bar is relative to the highest cell in its row. The highest stable result is highlighted, results within 10% of it are tied, and a result whose run-to-run variation (CV) is above 15% is labelled Unstable: it stays on the page with its samples but is never highlighted.</p>

<p class="bench-reading">The stacks were measured in 3 separate runs on the same machine (2026-11-23 16:54: Hinoki (Granian), FastAPI (Uvicorn), Django Ninja (Uvicorn), Django Bolt (Actix, native server); 2026-11-24 02:57: Hinoki (Kiso, native server); 2026-11-24 03:52: Fastify (Node.js), Hono (Node.js), Bun.serve (Bun)). The host load was not controlled between runs, so read a difference between stacks from different runs with that in mind.</p>

<p class="bench-reading">Granian is a third-party ASGI server; Kiso is Hinoki&#x27;s own Rust server (started with hinoki serve --server kiso). Both rows serve the same Hinoki application.</p>

<p class="bench-reading">Fastify, Hono and Bun.serve run on JavaScript runtimes (Node.js, Bun) instead of Python. They serve the same service, pass the same verifier and use the same number of processes, connections per process and CPU placement; their language, runtime and database driver differ.</p>

??? info "How the numbers are computed"

    All listed stacks passed the response and SQL statement-count verifier before measurement. Samples are pooled across server starts and none is discarded. Each sample is a fixed number of requests; `bombardier` counts non-2xx responses and failed requests as unexpected.

    - **Requests per second and latency are one measurement.** Every sample keeps the stated number of connections busy, so higher latency means fewer requests per second; the two do not confirm each other.
    - **Bars start at 0 and show the median requests per second.** Within a request type every stack shares one scale, and stacks keep a fixed order, so the page is not sorted into a ranking. The thin line on a bar is the lowest to highest sample.
    - **Samples are pooled, none is discarded.** A stack is started several times; the median, the range and the CV are computed over every sample of every start, and an unstable result lists them all.
    - **p50 and p99 are medians of per-sample percentiles**, not percentiles of all requests pooled together. A range is descriptive, not a confidence interval.
    - **A gap under 10% between two medians is a tie.** Differences that small are inside what this setup resolves, so no order is claimed. A larger gap is called a difference only when the sample ranges do not overlap.
    - **CV is the coefficient of variation of requests per second across samples.** Above 15% the result is labelled Unstable: its median and samples stay on the page, but it is not given the highest or tied mark and no comparison with it is claimed.
    - **What this does not cover:** TLS, proxies, authentication, compression, cold data, larger tables or other hardware. Pool sizes are equal per process, but each library schedules work differently. It is not a ranking and not a production claim.
