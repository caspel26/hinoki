Configure an application with settings¶

Updated November 25, 2026 13 min read

Settings are typed, immutable classes. You declare the fields your application needs; Hinoki adds the groups every application has, reads values from the environment, .env and TOML once, and refuses to start when something is wrong.

# notes/settings.py
from typing import Literal

from hinoki import settings


class ProjectSettings(settings.AppSettings, prefix="NOTES_", dotenv=".env"):
    database: settings.DatabaseSettings
    support_email: str = "support@example.com"
    stripe_key: settings.Secret | None = None
    theme: Literal["light", "dark"] = "light"

notes/main.py passes the class with Hinoki(settings=ProjectSettings), which loads it while building the application. Your fields are then on app.settings, and modules read them as ctx.settings.

Declare fields¶

A field without a default is required. Use plain types (str, int, bool, tuple[str, ...], Literal[...], X | None), settings.Secret for anything confidential, and a settings.Settings subclass for a group of your own. Settings types live in the hinoki.settings namespace (settings.AppSettings, settings.DatabaseSettings, settings.Secret, settings.Settings, settings.SettingsError); name your loaded value app_settings so the namespace is not shadowed.

settings.AppSettings brings the built-in groups: execution, lifecycle, logging, docs, server, pagination, cors, compression, metrics, security, events and admin, plus timezone, debug and allowed_hosts (see Hosts, CORS and HTTPS). docs.openapi_url, docs.docs_url, docs.redoc_url and docs.llms_url default to None; the generated main.py passes openapi_url and docs_url as Hinoki(...) arguments, which win over settings; the other two stay off. llms_url must start with /.

settings.DatabaseSettings is an optional field you declare in your own settings class, not a settings.AppSettings group. Its url defaults to sqlite://./.hinoki/local.sqlite3; max_size defaults to 10 connections per worker and must be at least 1.

settings.EmailSettings is optional in the same way: an email: settings.EmailSettings field installs the email module. Its backend (smtp, console or memory) is required and has no default; password is a Secret (NOTES_EMAIL__PASSWORD or NOTES_EMAIL__PASSWORD_FILE). Every field, its default and its range are in send email.

Where values come from¶

load is the only place configuration is read; Hinoki(settings=ProjectSettings) calls it for you. Highest first:

Source Example
overrides= in code (tests) ProjectSettings.load(overrides={"theme": "dark"})
the process environment NOTES_THEME=dark
a *_FILE variable (container secrets) NOTES_STRIPE_KEY_FILE=/run/secrets/stripe
the .env file the class names NOTES_THEME=dark in .env
the TOML file the class names theme = "dark" in settings.toml
the default in the class theme: ... = "light"

Name a TOML file on the class with toml="settings.toml" (a project created with --server granian already does). Tables map to groups: [database] with max_size = 12 sets database.max_size. TOML cannot hold settings.Secret values or the database URL; keep those in the environment or *_FILE files. load(prefix=..., dotenv=..., toml=...) overrides what the class declared. A TOML file named on the class or passed to load must exist and parse (an empty file is fine); a missing .env is skipped. Relative .env and TOML paths resolve from the current directory, so start the server from the project root.

Load the class yourself when module code needs a typed value before the application exists:

# notes/main.py
from hinoki import Hinoki

from notes.settings import ProjectSettings

settings = ProjectSettings.load()
app = Hinoki(settings=settings, title=f"Notes ({settings.theme})")

Routes, events, middleware and rules come from hinoki.toml, so Hinoki(...) needs no include=, events= or rules= here.

Variable names¶

The variable is the prefix plus the field name in capitals; a group nests with a double underscore.

Field Variable
support_email NOTES_SUPPORT_EMAIL
stripe_key NOTES_STRIPE_KEY
database.url NOTES_DATABASE__URL
execution.sync_workers NOTES_EXECUTION__SYNC_WORKERS
logging.format NOTES_LOGGING__FORMAT

Values are converted strictly: integers are ASCII digits (no 1_000, no 0x10), booleans are true/false/yes/no/on/off/1/0, lists are comma separated (use tuple[str, ...] to keep them immutable), Literal[...] takes one of its choices, and an empty value for X | None means None.

Mistakes fail at startup, all at once¶

A variable that starts with your prefix and looks like one of your settings but names no field is an error (a typo guard; strict=False turns it off). It looks like a setting when its first word starts a field's variable (NOTES_DATABASE_URL, NOTES_SERVER__PROT) or when it is spelt close to one (NOTES_THEMES). Other variables that only share the prefix belong to another program and are ignored: systemd's JOURNAL_STREAM does not break a project whose prefix is JOURNAL_. A missing required value, a bad number or a value that is not one of the choices is an error too, and every problem is listed together, with variable names and reasons but never values:

invalid settings:
  NOTES_EXECUTION__SYNC_WORKERS: must be an integer
  NOTES_DATABASE__MAX_SIZE: must be an integer
  NOTES_THEMES: unknown setting

Keep secrets secret¶

  • Declare them as settings.Secret (or settings.Secret | None). A settings.Secret (the same type as hinoki.Secret) prints as ********** in repr, str, logs and error messages, and as *** in describe() and the settings command; you get the real text only with secret.reveal(), at the one place that needs it (where the payment client is built: app_settings.stripe_key.reveal()).
  • Put secrets in the environment, a secret manager that exports variables, or files: with Docker or Kubernetes secrets set NOTES_STRIPE_KEY_FILE=/run/secrets/stripe; the file's content (without the trailing newline) is the value. Only a regular file up to 64 KiB is read; setting both NOTES_STRIPE_KEY and NOTES_STRIPE_KEY_FILE is an error.
  • A .env file is for development; never commit it. Pickling or serialising a settings object stores its secrets in plain text, so don't.
  • A validate() method you add to a group shows its message in errors, so never put a field's value in it.

See what is in effect¶

hinoki settings

NOTES_DATABASE__URL            environment  ***
NOTES_EXECUTION__SYNC_WORKERS  default      8
NOTES_STRIPE_KEY               file         ***
NOTES_THEME                    .env         dark

The second column is where each value came from: override, environment, .env, toml, file or default. The command reads the prefix, .env and TOML file the class declares; --prefix, --dotenv and --toml override them. --format json prints the same for tools, and --example writes a ready .env.example: every variable with its default and type, required values blank to fill in, and the optional ones with no printable default (secrets such as the database URL, values that default to unset) commented out, so a copied file keeps their defaults:

hinoki settings --example > .env.example

Logging and your own loggers¶

Declare loggers, handlers and formatters with a standard logging.config.dictConfig mapping, and point logging.config at it:

# notes/logs.py
LOGGING = {
    "version": 1,
    "formatters": {"short": {"format": "%(levelname)s %(name)s %(message)s"}},
    "handlers": {"console": {"class": "logging.StreamHandler", "formatter": "short"}},
    "loggers": {"orders": {"handlers": ["console"], "level": "INFO"}},
}

NOTES_LOGGING__CONFIG=notes.logs:LOGGING

The value may also name a function that returns the mapping. It is applied when each worker starts, right after Hinoki's own hinoki logger setup, with disable_existing_loggers off unless your mapping sets it. A mapping that configures the hinoki logger replaces Hinoki's handler on it. A target that cannot be imported or is not a mapping raises during startup. Kiso's access log is written by Kiso; set server.access_log_format = "logger" to route it through the hinoki.access logger.

Database connection ownership¶

A database: settings.DatabaseSettings field is all it takes: Hinoki installs DatabaseModule for it (a module declared in modules= replaces it). With nothing configured, the URL is the local SQLite file sqlite://./.hinoki/local.sqlite3, and the module creates its hidden directory and file when it starts. Configure a database covers the URL, the connection fields, TLS and each backend.

The module opens a pool in each worker's startup lifespan, fails startup if the database is unreachable, and closes that worker's pool on shutdown. Nothing connects when modules or models are imported. Each worker owns its own pool, so budget replicas × workers × max_size against the server database's connection limit.

One-off scripts have a different lifecycle: they open a short-lived Database themselves (use the database from a script). examples/blog/blog/apps/blog/seed.py does so, applies migrations, inserts synthetic rows and closes the pool in finally. It is a one-time seed for a fresh disposable database, not a repeatable reset:

cd examples/blog
export BLOG_DATABASE__URL=postgresql://app:password@localhost/blog
uv run python -m blog.apps.blog.seed

Use a disposable database for the example. The seed command is not a production migration mechanism and is not run at app startup.

Errors and edge cases¶

  • Setting both NOTES_STRIPE_KEY and NOTES_STRIPE_KEY_FILE is an error; only a regular file up to 64 KiB is read.
  • A variable with your prefix that looks like a setting (same first word, or a close spelling) but names no field is an error; other variables that only share the prefix, such as JOURNAL_STREAM, are ignored. Pass strict=False to load to turn the check off.
  • The server group is applied by hinoki dev and hinoki serve, not by other ASGI servers (Serving).
