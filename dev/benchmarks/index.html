Benchmarks¶

Updated November 24, 2026 20 min read

Measured: requests per second and latency of 9 stack setups on 7 request types of one small API backed by PostgreSQL. Where: AMD EPYC-Milan Processor, 8 logical CPUs, Linux-7.0.0-44-generic-x86_64-with-glibc2.43, 2026-11-24, 100 concurrent connections, median of 2 samples per cell.

Hinoki (Kiso, native server) against Hinoki (Granian): ahead in 4 of 7 request types, tied (within 10%) in 3, behind in 0.

Pre-alpha software, one host, warm data, loopback network: this is not a ranking and not a production claim.

Each cell is the median requests per second; higher is better. The bar is relative to the highest cell in its row. The highest stable result is highlighted, results within 10% of it are tied, and a result whose run-to-run variation (CV) is above 15% is labelled Unstable: it stays on the page with its samples but is never highlighted.

The stacks were measured in 3 separate runs on the same machine (2026-11-24 15:36: Hinoki (Granian), Django Bolt (Actix, native server), Litestar (Uvicorn), FastAPI (Uvicorn), Django Ninja (Uvicorn); 2026-11-24 16:50: Hinoki (Kiso, native server); 2026-11-24 18:31: Elysia (Bun), Hono (Bun), Hono (Node.js)). The host load was not controlled between runs, so read a difference between stacks from different runs with that in mind.

Granian is a third-party ASGI server; Kiso is Hinoki's own Rust server (started with hinoki serve --server kiso). Both rows serve the same Hinoki application.

Elysia on Bun, Hono on Bun and Hono on Node.js are the JavaScript servers of Django Bolt's comparison; they run on JavaScript runtimes instead of Python. They serve the same routes, pass the same verifier and use the same number of processes, connections per process and CPU placement; their language, runtime and database driver differ.

Each framework runs on the server Django Bolt's comparison uses: Hinoki on Granian, Litestar, FastAPI and Django Ninja on Uvicorn, Django Bolt on its own Actix server. A difference here can come from the server as well as from the framework.

Workloads, stacks and versions

One service with Django Bolt's seven routes, its tables and deterministic seed data: 10 users, 50 authors, 100 tags, 500 articles and 2,000 comments, plus the user of the JWT. Every stack had to match a PostgreSQL oracle and its expected SQL statement count per request before measurement (one extra statement on the tag routes for Hinoki, none elsewhere). The stacks differ in ORM, database driver and server, as listed below.

How the numbers are computed

All listed stacks passed the response and SQL statement-count verifier before measurement. Samples are pooled across server starts and none is discarded. Each sample is a fixed duration; bombardier counts non-2xx responses and failed requests as unexpected.

  • Requests per second and latency are one measurement. Every sample keeps the stated number of connections busy, so higher latency means fewer requests per second; the two do not confirm each other.
  • Bars start at 0 and show the median requests per second. Within a request type every stack shares one scale, and stacks keep a fixed order, so the page is not sorted into a ranking. The thin line on a bar is the lowest to highest sample.
  • Samples are pooled, none is discarded. A stack is started several times; the median, the range and the CV are computed over every sample of every start, and an unstable result lists them all. The exact tables also give the upper median, sorted(samples)[len // 2], the statistic Django Bolt's comparison publishes; with an even number of samples it is the higher middle sample.
  • p50 and p99 are medians of per-sample percentiles, not percentiles of all requests pooled together. A range is descriptive, not a confidence interval.
  • A gap under 10% between two medians is a tie. Differences that small are inside what this setup resolves, so no order is claimed. A larger gap is called a difference only when the sample ranges do not overlap.
  • CV is the coefficient of variation of requests per second across samples. Above 15% the result is labelled Unstable: its median and samples stay on the page, but it is not given the highest or tied mark and no comparison with it is claimed.
  • What this does not cover: TLS, proxies, compression, writes, cold data, larger tables, container memory limits or other hardware. Pool sizes are equal per process, but each library schedules work differently. It is not a ranking and not a production claim.
