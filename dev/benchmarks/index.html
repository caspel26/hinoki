Benchmarks¶

These measurements describe the recorded implementations, machines and workload only. They are not a universal comparison or a production-readiness claim. The primary metric is HTTP response time (p50, p95 and p99, in milliseconds, lower is better); requests per second is a secondary table in each slice. health is diagnostic; database-backed list, detail and create are the primary scenarios. No overall winner is calculated. Runs from different machines are shown in separate sections and must not be compared with each other.

Interpretation¶

Create varied by more than 15% (coefficient of variation of requests per second) in: the documented slice on Intel(R) Core(TM) i5-10300H CPU @ 2.50GHz, the same granian slice on Intel(R) Core(TM) i5-10300H CPU @ 2.50GHz. Treat write measurements in those slices, including their latency percentiles, as inconclusive for close comparisons; the median and range are descriptive and do not establish a winner.

Method and limits¶

Each stack used the same PostgreSQL seed and request/response oracle. The verifier checked response content, status and SQL statement counts before measurement. Create uses per-statement autocommit in each implementation. The documented-stack and same-Granian ASGI slices answer different questions: Bolt stays on its own server and is not included in the ASGI same-server control, so differences in the documented slice may come from the server as well as the framework.

Latency is the time oha measured from sending a request to receiving the full response, over loopback, with a fixed number of concurrent connections that send the next request as soon as one finishes. Latency and throughput are therefore linked (at fixed concurrency, higher latency means fewer requests per second) and are not independent evidence. Each percentile shown is the median of that percentile across the individual runs, with the lowest and highest run as the range; it is not a percentile of all requests pooled together. A min-to-max range is descriptive, not a confidence interval.

Each section is one host and one run window, and none was taken on an idle host: the load average at the start of each run is listed in its section. Drivers and ORM scheduling differ; equal pool settings do not imply identical behavior. The dataset is small and warm and this does not measure TLS, proxies, authentication, compression, memory, cold data or other workloads. Raw JSON, environment metadata, server logs, per-worker CPU time and verification output are retained in benchmarks/comparative/results/2026-11-15-macos-m4pro/, benchmarks/comparative/results/2026-11-15/; reproduction instructions are in benchmarks/comparative/README.md. Inspect them before drawing conclusions.
