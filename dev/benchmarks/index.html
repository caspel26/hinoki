Benchmarks¶

Updated November 21, 2026 22 min read

One API. Three server setups.¶

Four framework stacks served the same small API and PostgreSQL data. These measurements describe one machine and one benchmark session; they do not rank frameworks or predict production performance.

01Intel(R) Core(TM) i5-10300H CPU @ 2.50GHz028 logical CPUs03100 concurrent connections0410 samples per scenario

Read this first

Hinoki is pre-alpha. The run used one host, warm data and loopback networking. It is not a framework ranking or a production claim. Unstable samples stay visible as withheld results.

Results¶

How to read this

Each card and chart is one request type. Longer bars mean more requests per second on that workload; the number is the median of the measured runs. The multiplier (for example 2.00×) compares a stack with the slowest stack in the same chart, and Hinoki rows are drawn in the brand colour and bold type. Open "Exact numbers" under a chart for latency, the lowest and highest run and the run-to-run variation (CV).

Switch the server setup to compare each stack on its documented server, compare the three ASGI stacks on Granian, or see Hinoki on its own Rust server (Kiso). Each chart starts at zero and uses its own scale; exact values and run ranges are under each chart.

Each framework runs on the server it documents: Hinoki on Granian, FastAPI and Django Ninja on Uvicorn, Django Bolt on its own Actix server. A difference here can come from the server as well as from the framework.

What was measured¶

One service, two tables and deterministic seed data: 100 authors and 10,000 posts, 80% published. Every stack had to match a PostgreSQL oracle and the same SQL statement count per request before measurement. The stacks differ in ORM, database driver and server, as listed below.

How to read the numbers¶

Measurement notes and limits
  • Requests per second and latency are one measurement. Every sample keeps the stated number of connections busy, so higher latency means fewer requests per second; the two do not confirm each other.
  • Each chart starts at 0 and shows the median requests per second. Bars are sorted from highest to lowest within a workload and server setup. Each panel has its own scale; use the tables for exact values and the lowest-to-highest range.
  • The multiplier is one median divided by the slowest median in the same chart. It is a ratio of medians and carries their run-to-run spread; it does not compare charts with each other.
  • Samples are pooled, none is discarded. A stack is started several times; the median, the range and the CV are computed over every sample of every start, and the table also lists each start's own median.
  • p50 and p99 are medians of per-sample percentiles, not percentiles of all requests pooled together. A range is descriptive, not a confidence interval.
  • A gap under 10% between two medians is a tie. Differences that small are inside what this setup resolves, so no order is claimed.
  • CV is the coefficient of variation of requests per second across samples. Above 15% for any stack, the scenario is not reported: the samples are too unstable to compare, and the raw files are kept.
  • What this does not cover: TLS, proxies, authentication, compression, cold data, larger tables or other hardware. Pool sizes are equal per process, but each library schedules work differently.

Reproduce¶

go install github.com/codesenberg/bombardier@latest
cd benchmarks/comparative
uv sync --locked
VIRTUAL_ENV=$PWD/.venv uvx maturin develop --release --uv --manifest-path ../../crates/bindings/Cargo.toml
uv run --locked python run.py --server-mode documented --out results/YYYY-MM-DD/documented
uv run --locked python run.py --server-mode same-granian --out results/YYYY-MM-DD/same-granian
uv run --locked python run.py --server-mode kiso --out results/YYYY-MM-DD/kiso
uv run --locked python report.py results/YYYY-MM-DD/documented results/YYYY-MM-DD/same-granian results/YYYY-MM-DD/kiso > ../../docs/benchmarks.md

Raw bombardier JSON, environment records, server logs, per-worker CPU time and verification output are kept in benchmarks/comparative/results/2026-11-21/. Setup details, the database container and the rules for repeating an unstable scenario are in benchmarks/comparative/README.md.
