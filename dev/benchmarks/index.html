Benchmarks¶

Updated November 26, 2026 55 min read

Measured: requests per second and latency of 9 stack setups on 7 request types of one small API backed by PostgreSQL, with 8 workers (multi-process) and 1 worker (single-process). Where: AMD EPYC-Milan Processor, 16 logical CPUs, Linux-7.0.0-44-generic-x86_64-with-glibc2.43, 2026-11-25, 100 concurrent connections, median of 2 samples per cell.

Pre-alpha software, one host, warm data, loopback network: this is not a ranking and not a production claim.

Python frameworks

Hinoki (Kiso) is Hinoki's own Rust server and its default (started with hinoki serve --server kiso), as Actix is Django Bolt's; Hinoki (Granian) runs the same application on Granian, a third-party ASGI server. Every other framework runs on the server its documentation uses.

The stacks were measured in 2 separate runs on the same machine (2026-11-25 17:13: Hinoki (Granian), Django Bolt (Actix, native server), Litestar (Uvicorn), FastAPI (Uvicorn), Django Ninja (Uvicorn); 2026-11-25 16:53: Hinoki (Kiso, native server)). The host load was not controlled between runs, so read a difference between stacks from different runs with that in mind.

How the numbers are computed

All listed stacks passed the response and SQL statement-count verifier before measurement. Samples are pooled across server starts and none is discarded. Each sample is a fixed duration; bombardier counts non-2xx responses and failed requests as unexpected.

  • Requests per second and latency are one measurement. Every sample keeps the stated number of connections busy, so higher latency means fewer requests per second; the two do not confirm each other.
  • Bars start at 0 and show the median requests per second. Within a request table every stack shares one scale, and the reference stack comes first, then the others in a fixed order, so the page is not sorted into a ranking. The lowest to highest sample is in the last column.
  • The comparison column is the ratio of two medians, always at least 1 and worded in the direction it points (2.4× faster, 1.4× slower). It is computed from the same raw samples as the medians.
  • 8 workers and 1 worker are separate runs. Each stack is started with that many server processes (and the same pool per process); the two groups are not added together and a 1-worker number says nothing about scaling.
  • Samples are pooled, none is discarded. A stack is started several times; the median, the range and the CV are computed over every sample of every start, and an unstable result lists them all. The exact tables also give the upper median, sorted(samples)[len // 2], the statistic Django Bolt's comparison publishes; with an even number of samples it is the higher middle sample.
  • p50 and p99 are medians of per-sample percentiles, not percentiles of all requests pooled together. A range is descriptive, not a confidence interval.
  • A gap under 10% between two medians is a tie. Differences that small are inside what this setup resolves, so no order is claimed. A larger gap is called a difference only when the sample ranges do not overlap.
  • CV is the coefficient of variation of requests per second across samples. Above 15% the result is labelled Unstable: its median and samples stay on the page, but it is not given the highest or tied mark and no comparison with it is claimed.
  • What this does not cover: TLS, proxies, compression, writes, cold data, larger tables, container memory limits or other hardware. Pool sizes are equal per process, but each library schedules work differently. It is not a ranking and not a production claim.
